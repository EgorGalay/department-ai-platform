# Department AI Platform — архитектура

## Назначение

Локальная AI-платформа кафедры на собственном сервере. Пользователи работают через единый веб-интерфейс, а подключаемые модули используют общий backend и локальные AI-сервисы.

Первые прикладные направления: помощник по учебным материалам (RAG), обработка и оформление документов, образовательный и исследовательский помощники. MCP-инструменты и лаборатория безопасности LLM — расширения следующих этапов.

## Общая архитектура

| Компонент | Роль |
|---|---|
| Frontend — Next.js | Интерфейс студентов, преподавателей и администраторов; обращается только к backend API |
| Backend — FastAPI | Авторизация, API, сценарии приложения, управление модулями и доступом к данным |
| Бизнес-модули | Документы, база знаний/RAG, образовательные и исследовательские функции |
| Локальная LLM и embedding-модель | Генерация ответов и векторизация текста через заменяемые адаптеры |
| PostgreSQL | Основные структурированные данные и метаданные; доступ через SQLAlchemy и миграции Alembic |
| Qdrant | Векторный поиск по фрагментам документов |
| Файловое хранилище | Исходные и сформированные документы |
| Очередь задач | Длительная обработка документов и фоновые задачи |

### Границы слоёв

| Слой | Ответственность |
|---|---|
| Presentation | HTTP API, WebSocket/SSE и проверка входных запросов; без бизнес-правил |
| Application | Сценарии использования и их оркестрация; не зависит от FastAPI и конкретной БД |
| Domain | Сущности, правила и интерфейсы; не знает о Docker, HTTP и провайдерах моделей |
| Infrastructure | Реализация доступа к БД, LLM, файлам и очереди; не определяет бизнес-правила |
| Frontend | UI, пользовательские сценарии и клиентское состояние; не подключается напрямую к БД или LLM |

Модули добавляются через общие API и контракты. Замена модели или реализации хранилища не должна менять бизнес-правила модулей.

## Данные

PostgreSQL хранит пользователей, организации, членство и роли, курсы, диалоги и сообщения, шаблоны и версии промптов, события аудита, базы знаний и метаданные документов. Схема развивается миграциями Alembic. Исходные файлы хранятся отдельно; Qdrant содержит векторы и ссылки на соответствующие документы/фрагменты.

Основные связи предметной модели:

- организация содержит пользователей и курсы;
- пользователи создают диалоги и события аудита, а также вступают в курсы;
- курсы включают участников и базы знаний;
- база знаний содержит документы, документы разбиваются на фрагменты;
- диалог содержит сообщения;
- шаблон промпта имеет версии.

Начальная миграция создаёт организации, пользователей и членство пользователя в организации с ролью `admin`, `teacher` или `student`. Остальные сущности добавляются вместе с соответствующими пользовательскими сценариями.

Это логическая модель. Поля, ограничения и точные связи уточняются при проектировании миграций.

## Frontend и обмен данными

Next.js предоставляет единый web-интерфейс. Он отправляет запросы в FastAPI и получает результаты через HTTP API; потоковые ответы при необходимости передаются через SSE или WebSocket. Backend проверяет права и сам обращается к PostgreSQL, Qdrant, файловому хранилищу и локальной модели. Прямых подключений frontend к этим сервисам нет.

## Основные этапы реализации

1. **Основа платформы:** структура проекта, конфигурация, запуск backend и frontend, локальное окружение.
2. **Общий контур:** пользователи, роли, API-контракты, PostgreSQL и базовые операции с данными.
3. **AI Core:** подключение локальной LLM и embedding-модели через адаптеры.
4. **Первый прикладной сценарий:** загрузка документов, их обработка, база знаний и ответы RAG с источниками.
5. **Пользовательские модули:** оформление документов, образовательный и исследовательский помощники.
6. **Расширение платформы:** MCP-инструменты и изолированная Security Lab после готовности основного контура.
7. **Подготовка к эксплуатации:** доступы, журналирование, резервное копирование и мониторинг.
