# План реализации кода

План описывает порядок разработки Department AI Platform небольшими рабочими частями. Цель первого релиза — платформа, в которой преподаватель загружает учебные материалы, а пользователь задаёт по ним вопросы и получает ответ с источниками.

## Принципы разработки

- Делать один рабочий пользовательский сценарий за раз, от API до интерфейса.
- Оставлять приложение модульным монолитом: отдельные модули в одном backend, без раннего разбиения на микросервисы.
- Добавлять только нужные классы и слои. Не создавать заранее общие фабрики, реестры плагинов, event bus или универсальные фреймворки.
- Внутри модуля разделять API, сценарии, бизнес-правила и интеграции там, где это упрощает изменение и проверку кода.
- Внешние системы (PostgreSQL, Qdrant, файловое хранилище, Qwen) вызывать только из backend. Технологические детали не помещать в бизнес-правила.
- Следовать coding-workflow: перед изменением нескольких файлов кратко определить затрагиваемые файлы и проверку; читать только нужные части; проверять изменённый сценарий релевантными командами, когда проверка запрошена.

## Этапы

### 1. Запуск каркаса

**Сделать:** заполнить текущие `main.py`, `bootstrap.py`, настройки приложения и health endpoint; добавить локальную конфигурацию и команды запуска backend. Поднять минимальную Next.js оболочку в `frontend/`.

**Готово, когда:** backend запускается, health endpoint отвечает, frontend открывается, настройки читаются из окружения, секреты не хранятся в Git.

### 2. Основа хранения данных

**Сделать:** подключить PostgreSQL и миграции; определить минимальные модели пользователя, организации и членства с ролью; добавить проверку готовности базы данных.

**Готово, когда:** схема создаётся миграцией, backend использует одну сессию БД на запрос, readiness endpoint показывает доступность БД. На этом шаге публичных endpoint’ов управления пользователями нет.

### 3. Доступ пользователей

**Сделать:** создать первого администратора интерактивной командой; реализовать вход, профиль текущего пользователя и серверную проверку ролей для закрытых endpoint’ов.

**Готово, когда:** пользователь может войти, получить профиль, а backend применяет права организации и роли. Открытую регистрацию, сброс паролей и интеграцию с университетским каталогом отложить.

### 4. Связь с локальной LLM

**Сделать:** реализовать один backend-клиент для существующего Qwen API с адресом из конфигурации; добавить простой сценарий вопрос–ответ и сохранение диалога.

**Готово, когда:** backend отправляет запрос локальной модели, возвращает ответ и сохраняет историю. Переключение на несколько моделей и бенчмарки оставить на будущее.

### 5. Первая база знаний (RAG)

**Сделать:** загрузку файлов; хранение файла и метаданных; извлечение текста, разбиение на фрагменты, embeddings, индексирование в Qdrant; поиск по выбранной базе знаний; ответ модели с найденными фрагментами и ссылками на источник.

**Готово, когда:** пользователь загружает материал, задаёт вопрос по нему и получает ответ с проверяемыми источниками; доступ к материалам проверяется backend.

### 6. Минимальный интерфейс RAG

**Сделать:** страницы входа, списка баз знаний, загрузки материалов и чата; отображение загрузки, ошибок и источников ответа; общение только с backend API.

**Готово, когда:** основной сценарий полностью выполняется из браузера без прямого доступа frontend к БД, Qdrant или модели.

### 7. Обработка и оформление документов

**Сделать:** отдельный сценарий загрузки DOCX/PDF, проверки структуры и применения шаблона кафедры; выдачу результата отдельным файлом. Форматирование выполнять детерминированной обработкой/шаблонами, LLM использовать для анализа и подсказок.

**Готово, когда:** исходный документ не теряется, пользователь может скачать сформированный результат и видит ошибки обработки.

### 8. Следующие помощники

**Сделать:** образовательный и исследовательский сценарии поверх уже работающей базы знаний и AI-клиента. Каждый добавлять отдельной завершённой функцией с собственным API и интерфейсом.

**Готово, когда:** каждый помощник решает конкретную задачу кафедры и использует существующие сервисы без дублирования доступа к моделям и данным.

### 9. Эксплуатация и расширения

**Сделать:** резервное копирование, журналирование, мониторинг и ограничение ресурсов; добавить очередь для действительно долгих фоновых задач. После основного контура рассматривать MCP и изолированную Security Lab.

**Готово, когда:** развёртывание и восстановление описаны, ошибки и состояние сервисов видны, а новые интеграции не требуют переписывать существующие модули.

## Минимальные границы кода

- `api/` — маршруты и проверка/преобразование HTTP-запросов.
- `modules/<module>/` — только реализуемые функции платформы; не заполнять все заранее созданные пустые каталоги.
- `infrastructure/` — клиенты к БД, Qdrant, файлам и Qwen по мере их подключения.
- `core/` — общая конфигурация, ошибки и логирование без бизнес-функций.
- `frontend/` — страницы и компоненты клиента; обращения к данным идут через backend API.

## Не включать в первый релиз

Микросервисы, универсальный конструктор workflow, динамический реестр произвольных плагинов, несколько LLM-провайдеров, MCP-агенты и Security Lab. Эти направления добавляются только после работающего базового сценария и конкретной потребности.
